解決遺留系統負債，建立具備擴充性與單一真實來源之資料生態系

高階主管摘要 (Executive Summary)

本報告旨在解決大型機構面臨之資料孤島與異質系統編碼衝突問題。透過建立統一治理框架、實施中介層防護網，並強制推行單一真實來源 (SSOT) 策略，我們將協助機構將資料負債轉化為戰略資產，降低維運風險並提升跨部門協作效率。

機密文件 - 僅供內部決策參考 頁 1

歷史遺留系統與各自為政的開發模式，正導致嚴重的資料冗餘與系統風險

在缺乏統一架構治理的情境下，機構正承擔兩大核心資料風險，直接影響營運效率與後續數位轉型：

風險一：資料孤島與架構膨脹

Data Silos & Schema Bloat

  • 各業務單位（如 HR、財務）對同一業務實體提出重複需求。
  • 缺乏查核機制，導致同一資料庫中出現多個本質相同但命名不同的欄位（如：緊急電話 vs. 家屬手機）。
  • 結果：資料更新不同步，無法建立單一視圖 (Single View of Truth)。

風險二：異質編碼導致系統失靈

Encoding Inconsistency

  • 老舊核心系統（如 Big5 編碼）與現代化應用程式（如 UTF-8 編碼）直接共用底層資料庫。
  • 缺乏轉碼防護，導致寫入與讀取時頻繁出現「亂碼 (Mojibake)」。
  • 結果：關鍵搜尋功能失效，並需要耗費大量人力進行人工資料校正。
現況診斷分析 頁 2

建立嚴謹的資料治理流程與實體架構標準，是根除資料重複的基石

1. 流程與治理面重塑 (Governance Re-design)

  • 設立架構審查關卡： 終止「需求直達開發」的模式。所有資料庫變更需經由資料架構師 (Data Architect) 進行業務本質分析與需求收斂。
  • 導入企業級資料字典： 建立全機構共用的 Master Data 綱要（Data Dictionary）。新需求應優先執行「查表比對」，最大化欄位復用率。
  • 確立資料擁有權 (Data Ownership)： 明確界定各資料域的「擁有者（如人事處掌控地址資料）」，其餘單位僅具讀取與檢視權限。

2. 實體架構與標準化 (Physical Architecture)

  • 主檔與明細解耦： 核心實體集中於主檔（Master Tables），業務關聯表單僅儲存識別碼（Foreign Keys）。
  • 多重屬性擴展機制： 具備一對多特性的資料（如多組聯絡人），應建立獨立明細表，以「類型代碼」區分，嚴禁水平擴展單一表單。
  • 強制統一底層編碼： 資料庫實體層級之 Collation 必須實施絕對標準化（建議採用 UTF8MB4），對混合編碼採取零容忍政策。
策略建議：治理與架構 頁 3

實施「中介層防護網」，徹底阻絕異質系統造成的髒資料直寫入底層庫

核心戰術方針：剝奪老舊系統的直接連線存取權 (Revoke Direct Access)

為解決編碼衝突與確保寫入邏輯一致性，必須在應用系統與資料庫之間建立隔離層：

A. 部署中介網關 (Middleware / API Gateway)

全面禁止老舊系統（Legacy Systems）直接發送 SQL 指令至核心資料庫。所有寫入動作必須路由至中介層（API 或 Database Proxy）進行統一處理與驗證。

B. 強制雙向轉碼 (Bi-directional Encoding Conversion)

在中介層建置自動轉譯機制。針對使用舊式編碼（如 Big5）的請求，由中介層攔截並轉換為標準 UTF-8 後執行寫入；讀取時反向轉譯，確保不影響舊系統既有運作。

C. 連線字串的嚴格控管 (Connection String Management)

全面盤點並標準化所有應用程式之資料庫連線字串，強制顯性宣告編碼參數（如 characterEncoding=UTF-8），消除對作業系統環境變數之依賴風險。

策略建議：系統整合與防護 頁 4

透過視圖客製化與非結構化擴充，兼顧跨單位需求彈性與核心架構穩定

3. 展現層分離與客製化 (Presentation Tier)

在不更動底層共用欄位的前提下，滿足各業務單位之客製化術語需求：

  • 客製化資料庫視圖 (DB Views)： 針對不同單位建立專屬 View，透過 Alias 將共用欄位映射為該單位的業務專有名詞。
  • API DTO 動態映射： 利用現代化後端架構，於回傳層 (Data Transfer Object) 動態轉換 JSON Key，實現「底層單一、表層多元」。

4. 彈性防護與資料清理 (Flexibility & Remediation)

針對冷門需求與歷史包袱的處置策略：

  • JSON / EAV 模型擴充： 面對低頻、高客製之孤立屬性，採用非結構化 JSON 欄位或 EAV (Entity-Attribute-Value) 模式儲存，遏止核心 Schema 之無序擴張。
  • 歷史髒資料清洗專案 (Data Cleansing)： 針對既有之亂碼或重複紀錄，應立案專屬 ETL 專案，輔以特徵比對演算法進行批次正規化與轉譯。
策略建議：彈性擴充與清理 頁 5
